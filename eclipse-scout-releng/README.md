# Eclipse Scout - Releng

Contains release engineering scripts for the [Eclipse Scout](https://www.npmjs.com/package/@eclipse-scout/core) framework.

## Scout overrides

The `install` command pins the versions of all transitive dependencies of the pnpm workspace using
[overrides](https://pnpm.io/settings#overrides). Snapshot dependencies and dependencies already declared with a fix version are not pinned.

The generated overrides are written into the `overrides` of each `pnpm-workspace.yaml`, between two marker comments:

```yaml
overrides:
  # manual overrides, not touched by the generator
  foo: 1.2.3
  # >>> generated by @eclipse-scout/releng, do not edit until the end marker
  lodash@4.17.21: 4.17.21
  parent>lodash@4.17.20: 4.17.20
  parent>my-alias: npm:other@1.0.0
  # <<< end of generated overrides
```

Each generated override has the pinned version as version selector of the dependency (`lodash@4.17.21`). pnpm applies such an override only to dependencies
whose declared range includes this version. So the override pins the version wherever it is compatible, but does not force it on a package requiring another
version:

- A dependency whose range was changed in a `package.json` and no longer includes the pinned version is resolved anew.
- A package updated to a new version (e.g. a snapshot) with other ranges for its own dependencies gets dependencies matching these ranges.

The next generation pins the newly resolved versions. Overrides of npm aliases (`npm:<name>@<version>`) have no version selector, as pnpm does not match a
version selector with a dependency declared as npm alias.

A dependency used as peer dependency by an installed package gets overrides with parent only (e.g. `espree@7.3.1>acorn@7.4.1`), also if it is installed in a
single version. pnpm also applies an override without parent to the peer ranges of the packages using it: it would replace the peer range with the pinned version
and cause unmet peer dependencies wherever another version is provided.
Optional peer dependencies declared in the `peerDependenciesMeta` only count as peer dependencies too. The dependencies of a peer dependency get overrides only
if they are reached through a package providing it: if pnpm takes a peer dependency from another project or installs it itself, its dependencies would not be
installed when the workspace of a nested `pnpm-workspace.yaml` is installed on its own.
If the overrides used by the install contained an override of a peer dependency that is removed (e.g. a global override migrated from the former format, or
generated before a newly added package declared the dependency as peer), this override may have influenced the resolution of the peer dependency. Then the scout
install runs `pnpm update` and the update of the overrides once more, so that the result does not change on the next install.

- Only the entries between the markers are replaced. Overrides outside the markers (e.g. written manually or by `pnpm audit --fix`) are not changed.
- The markers are added at the end of the `overrides` if they are missing. Do not remove only one of them: the generator fails if a marker is missing or duplicated.
- With `--updateMode=all`, the generated overrides are temporarily turned into comment lines between the markers.
- A `pnpm-workspace.yaml` using the former format (a `scout.overrides` block merged into the `overrides` using `<<: *scout-overrides`) is migrated automatically:
  the `scout` block and the merge key are removed and the generated overrides are written between the markers at the position of the merge key. The overridden
  version is added as version selector (`lodash: 4.17.21` becomes `lodash@4.17.21: 4.17.21`), so that pnpm no longer forces it on dependencies whose range does
  not include it. With `--updateMode=required`, the scout install migrates the `pnpm-workspace.yaml` before running `pnpm update`.

### Manual overrides

Overrides outside the markers are not touched by the generator. No override is generated for the same parent and dependency as a manual override, regardless of
the versions in the selectors: e.g. the manual override `lodash: 4.17.20` prevents the generated `lodash@4.17.21`, and `app>lodash: 4.17.20` prevents
`app@1.0.0>lodash@4.17.21`.

pnpm does not distinguish manual from generated overrides, but applies the most specific override to a dependency:

1. Overrides with a parent (`<parent>><dependency>`) take precedence over overrides without (`<dependency>`), regardless of their position.
2. Among overrides with a matching parent (or among the ones without parent), the one with the narrowest version selector of the dependency wins
   (`<dependency>@1.2.3` over `<dependency>`). A version of the parent does not count: of `<parent>@1.0.0><dependency>` and `<parent>><dependency>` the first
   one in the file wins.

As a consequence, a manual override without parent (e.g. `lodash: 4.17.20`) does not replace the generated overrides with a parent
(e.g. `parent>lodash@4.17.21`). To pin a dependency for a single package, write a manual override with this package as parent.

## Deploy

1. Check that there are no *.js files in the module. If there are old build artifacts: remove them first.
2. Update version in `package.json`: set to a unique new version without `-snapshot` suffix.
3. Run tests using npm script `npm run test`.
4. Build using npm script `npm run build`.
5. Deploy to a local registry to test the new package: `npm publish --registry http://127.0.0.1:4873/`.
6. If all is fine: Deploy to real registry: `npm publish` (requires corresponding access token in your `.npmrc`).
